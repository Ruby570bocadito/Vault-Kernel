## Hallazgo 1 (clase nueva) — los VALORES de flag que empiezan por `-`

La matriz de la ronda 6 verificaba CUÁNTOS operandos aceptaba cada
comando. Esta ronda la extiende a QUÉ acepta como valor de un flag con
argumento. Resultado:

| Input | Go (pre-v3.10) | Python (argparse) |
|-------|----------------|-------------------|
| `keylog --output --follow` | ACEPTA; outputPath = `"--follow"`; el error aparece al abrir el dispositivo (o, con módulo cargado, crea un fichero llamado `--follow`) | RECHAZA (`expected one argument`) |
| `capture --out --json` | ACEPTA; outPath = `"--json"` | RECHAZA (`expected one argument`) |
| `keylog --output -foo` | ACEPTA (fichero `-foo`) | RECHAZA en forma espaciada (argparse trata `-foo` como opción); acepta la forma `--output=-foo` |

Verificado por reproducción real en este entorno: el binario Go
construido de `7722353` acepta los tres inputs (el fallo llega después,
al abrir `/dev/vault_kernel`, que es lo que oculta la brecha de
gramática en un lab sin módulo), y el CLI Python rechaza el primero con
error de argparse.

**Clasificación del Director:** misma familia que el hallazgo
sistémico de la ronda 6 (errores de uso silenciosos), pero en la
capa de VALORES: el parser Go de flags con operand (`--output`,
`--out`) consume el token siguiente sin ninguna validación de
contenido. El plan de esta ronda instala la regla global en los DOS
parsers (rechazo de valores que empiezan por `-`, con mensaje que
enseñe el escape `./-foo`) en vez de parchear llamadas.

## Hallazgo 2 — `stats --json` Python: el camino de error vacío no es JSON

Con el dispositivo devolviendo un reporte vacío, `stats(as_json=True)`
de Python imprime el texto `(no stats returned)` y **sale 0** — el
consumidor de JSON recibe texto no-JSON con código de éxito. El cliente
Go (`showStatsJSON`) falla con `module returned an empty stats report`
y exit 1. Brecha de paridad en el camino de error: mismo comando, misma
situación, dos comportamientos según cliente. Causa: la rama
`if not output` se evalúa ANTES que `elif as_json` en
`VaultKernelClient.stats`. El plan la reordena (JSON primero) con test
de regresión en ambos sentidos.

## Hallazgo 3 — señales: SIGTERM mata a mitad de stream y la despedida de Ctrl-C no es paritaria

- `keylog --follow` (ambos clientes) solo termina limpio por
  KeyboardInterrupt (Ctrl-C). Un `systemd stop`, `pkill -TERM` o el
  cierre de una sesión de lab mata el proceso DURANTE el bucle: el sink
  de `--output` se queda sin cerrar ordenado y el operador no recibe
  mensaje de parada.
- Paridad rota en la despedida: Python imprime `\n[*] Follow stopped`
  en Ctrl-C; Go sale en silencio (manejo por defecto de SIGINT).
- `watch` Go captura SIGINT pero no SIGTERM (y `watch` Python tampoco):
  el cursor de consola puede quedar oculto si la terminación llega por
  TERM — el `finally` de Python no se ejecuta en SIGTERM por defecto.

El plan: SIGTERM capturado y enrutado por el mismo camino de parada
limpia en los CUATRO bucles largos (keylog Go/Python, watch Go/Python),
y el mensaje `[*] Follow stopped` unificado en ambos clientes.

## Hallazgo 4 — `status`: paridad textual y ausencia de salida JSON

- Python `status` enriquece la salida con `modinfo vault_kernel`
  (líneas que contienen version/author/description); Go imprime solo el
  estado del nodo — el operador del binario principal no ve la versión
  del módulo instalado.
- Ningún cliente ofrece `status --json`: la comprobación "¿está
  plantado?" — la más natural para scripts de lab — es la única
  superficie de estado SIN documento JSON (stats/list/doctor/capture la
  tienen; es el quinto documento natural del contrato).
- El emparejamiento por SUBSTRING de Python imprime también
  `srcversion:` (contiene "version") — menor, pero el parser exacto
  que trae el plan lo deja determinista en ambos clientes.

El plan convierte `status --json` en el QUINTO documento JSON
(`docs/schemas/status.md`), añade modinfo al `status` Go (paridad),
reemplaza el substring-matching por `parse_modinfo` exacto en ambos, y
añade el par `--version`/`-v` al CLI Python (Go lo tiene desde v3.6).

## Falsos positivos del canal de render en esta ronda

UNO nuevo, y es el más serio de la serie: durante el smoke del fix de
valores de flag, el canal mostró `--follow s]]` donde el disco tenía
`--follow [ms]]` — y esta vez el artefacto SOBREVIVIÓ a `cat -A`
(dump de bytes "crudo"). Sólo la aritmética pura (conteo de
ocurrencias de ambos needles con etiquetas libres de corchetes)
resolvió la duda: `[--follow [ms]]` ×3, `[--follow s]]` ×0 — el
fichero está BIEN y el commit de la ronda 6 fue correcto al no
"arreglarlo". Conclusiones operativas, elevadas a política: (1) el
canal consume la secuencia `[m` (SGR reset) aunque no haya ESC
delante, y lo hace TAMBIÉN dentro de dumps `cat -A` y `repr()`; (2)
`od -c`/`grep -F` dejan de ser la fuente de verdad recomendada para
este caso y pasan a serlo los CONTEOS con etiquetas sanitizadas
(ADR 18 se actualiza en espíritu; el texto del ADR 18 no se reescribe
— la lección queda registrada en este informe y en el de ROL 4).

Las otras dos sospechas de la lectura (guiones largos del panel,
corchetes de usage texts) se resolvieron con el mismo método: bytes
correctos en disco.
