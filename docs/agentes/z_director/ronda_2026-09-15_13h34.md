## Hallazgo 1 (SISTÉMICO) — la matriz comando×cliente de gramáticas

Metodología nueva de esta ronda: para cada uno de los 21 comandos del
CLI Go se verificó programáticamente qué hace con (a) sin operandos,
(b) operandos justos, (c) operandos de MÁS, (d) flags desconocidos —
y se comparó con la gramática argparse de Python del mismo comando.
Resultado agregado:

| Comando | Exceso de args en Go (pre-v3.9) | Python |
|---------|-------------------------------|--------|
| `give-root` | estricto (fix ronda 5) | estricto |
| `keylog` | estricto (fix ronda 5) | estricto |
| `hide-file`/`unhide-file` | `hide-file a b` oculta "a", ignora "b" | rechaza |
| `hide-pid`/`unhide-pid` | ignora exceso | rechaza |
| `hide-port`/`unhide-port` | ignora exceso | rechaza |
| `list`/`stats` | `list extra` lista igual; `list --json extra` ignora extra | rechaza |
| `watch` | `watch --interval 500 extra` ignora "extra" | rechaza |
| `shell` | ignora exceso; target solo exige "contiene :" | rechaza exceso; target: SIN validación |
| `magic` | ignora exceso | rechaza |
| `magic-encode` | ignora exceso de args | rechaza (argparse) |
| `keylog-clear`/`hide-module`/`unhide-module`/`reset` | ignora exceso | rechaza |
| `status`/`version`/`doctor` | ignoran exceso / `doctor extra` corre igual | rechaza (doctor) / status sin args |

**15 de 20 cases del dispatcher Go** ignoraban argumentos sobrantes.
Clasificación del Director: no es un bug, es una CLASE de bug con una
causa estructural (el dispatcher creció por adición de cases, cada uno
con su validación ad-hoc de "mínimo de operandos", sin regla global de
gramática). El plan de esta ronda instala la regla global
(`strictArgs`/`parseFlagOnly`/parsers puros) en lugar de parchear casos.

## Hallazgos 2-5 (concretos, todos verificados)

2. **`shell` sin validación real en ningún cliente.** Go: solo
   `strings.Contains(target, ":")` — `shell abc:def` pasaba el cliente
   y moría en el kernel con EINVAL crudo (el módulo parte en el PRIMER
   `:` y `kstrtoint("def")` falla). Python: NO validaba NADA — cualquier
   string llegaba al ioctl. Verificado leyendo el camino completo
   cliente→`src/ioctl.c`→`backdoor_trigger_shell`.
3. **`hide-pid`/`unhide-pid` aceptan pid ≤ 0 en ambos clientes.** El
   módulo (`src/proc_hide.c: proc_hide_add`) almacena CUALQUIER int
   verbatim en la hide-list: `hide-pid -5` produce una entrada
   "pid: -5" en `list` que nada puede igualar nunca (`hooked_kill`
   filtra solo pid > 0; `is_proc_pid_hidden` parsea dígitos). Dato
   corrupto por diseño del contrato kernel; la barrera correcta es el
   cliente.
4. **Bug de paridad real: `keylog` one-shot de Python con buffer
   vacío no imprime NADA.** El flujo v3.8: `if cur != prev:` — con
   buffer vacío `cur == prev == ""` y el print cae en la rama que no
   se ejecuta. Go imprime `[*] (no keystrokes captured)`. Arrastrado
   desde v3.5 (nunca hubo test del camino vacío one-shot).
5. **Errores documentales del README** (verificados por conteo contra
   el código): "17 ioctls/commands" en dos sitios (mermaid + árbol) —
   real: **16** (0x01–0x10, conteo cruzado core.h↔Go↔Python: 16/16/16
   ✓); "cmd/vault_kernel/ # 18 comandos" — real: **21** subcomandos.

## Decisiones tomadas por el Director en esta ronda

- **El módulo kernel sigue intocado** (4ª ronda): todas las barreras
  nuevas viven en los clientes, que son testeables sin VM. El contrato
  del módulo (pid<=0 = caller en give-root, primer-`:` en shell) NO
  cambia; los clientes lo respetan y añaden la validación que falta.
- **`help`/`-h` quedan permisivos con argumentos extra** deliberadamente:
  es una página de ayuda, no una operación con estado; estricto ahí
  solo añadiría fricción. Decisión documentada (los otros 20 comandos
  son estrictos).
- **La suite de completions es funcional, no solo sintáctica:** el
  script se diseña autocontenido (sin paquete bash-completion)
  precisamente para que el test pueda sourcearlo y manejar
  COMP_WORDS/COMP_CWORD directamente en cualquier CI.
- **Presupuesto de la ronda:** triplicar esfuerzo NO tocar el módulo:
  el esfuerzo extra va íntegro a producto de cliente, paridad
  estructural y contrato documentado.
