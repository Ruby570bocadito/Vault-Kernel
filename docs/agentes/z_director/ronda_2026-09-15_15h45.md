## Hallazgo 2 (MEDIA-BAJA, control plane) — el aviso de no-root rompe el contrato sin-root de v3.10

Reproducido en este entorno sobre el commit base:

```
$ python3 vault_kernel_cli.py status --json 2>/dev/null | head -2
[!] Warning: not running as root. Some commands may fail.
{
  "schema": 1, ...
$ python3 vault_kernel_cli.py status --json | python3 -c 'import json,sys; json.load(sys.stdin)'
Traceback (most recent call last): json.decoder.JSONDecodeError
```

- El CLI Python imprime el aviso en STDOUT (main(), antes del
  dispatch, sin distinción de comando): el documento JSON de
  `status --json` llega precedido de texto plano y CUALQUIER
  consumidor (`jq`, `python -c json`) muere — para el usuario no-root,
  que es el destinatario declarado del comando desde v3.10
  ("el quinto documento, consumible sin root").
- El binario Go avisa también SIEMPRE, pero por STDERR (jq-safe);
  sigue siendo ruido para `status`/`version`/`help`/`magic-encode`,
  comandos que nunca abren el dispositivo.
- **Clasificación:** la superficie de AVISOS es parte de la matriz
  comando×cliente (nueva fila): un stderr limpio es contrato en
  workflows scriptados.

El plan (ROL 4): el aviso solo se emite para comandos que abren el
dispositivo (`deviceRequired`/`_NO_ROOT_REQUIRED`, MISMA lista en
ambos clientes por contrato de paridad) y SIEMPRE por stderr; test de
regresión con subproceso REAL que parsea el stdout y exige stderr
vacío.

## Hallazgo 3 (BAJA, clase gramatical cerrada en rondas 6-7) — la convención POSIX `--` está partida

Reproducido contra argparse (exit codes reales) y contra el binario Go
sobre el commit base:

| Input | Go (pre-v3.11) | Python (argparse) |
|-------|----------------|-------------------|
| `hide-file -foo` | ACEPTA (manda "-foo" al kernel) | RECHAZA (exit 2, "no such option") |
| `hide-file -- -foo` | RECHAZA (usage: 2 operandos) | ACEPTA (name="-foo") |
| `magic-encode -- -pwn 4444` | RECHAZA | ACEPTA (word="-pwn") |
| `hide-file -` | ACEPTA | ACEPTA (stdin-style) |
| `give-root -5` | ACEPTA (pid=-5) | ACEPTA (número negativo = posicional) |
| `magic -pwn` | ACEPTA | RECHAZA |

- **Clasificación:** la MISMA familia que los hallazgos sistémicos de
  las rondas 6 (operandos posicionales) y 7 (valores de flag), en la
  célula que faltaba: el ESCAPE POSIX y los valores con guion de los
  OPERANDOS POSICIONALES. Dos gramáticas para el mismo comando según
  el cliente.
- El plan (ROL 4): `posixOperandArgs` en Go con la semántica EXACTA
  de argparse — el escape `--` entrega verbatim, el `-foo` desnudo se
  rechaza nombrando el token y enseñando el escape, `-` y los
  números negativos permanecen verbatim (contrato `give-root -5` =
  self intacto) — cableado en los NUEVE comandos con operandos
  posicionales y tabla fijada por `TestPosixOperandArgs`.

## Hallazgo 4 (instrumental) — el canal de render consumió `[m` de nuevo

Durante la edición de la usage-line de `keylog`, el canal mostró
`[--follow s]]` donde el disco tenía `[--follow [ms]]` (cuarta
aparición de la serie). Resuelto con el método ADR 18 vigente:
conteos con etiquetas sanitizadas — `keylog [--follow [ms]] ...` ×3,
`[--follow s]]` ×0 — el fichero estaba BIEN y no se tocó. Además, la
misma sesión destapó una trampa de EDICIÓN nueva: el uso de
old-strings renderizadas (con tabs expandidos a espacios) convirtió
TODO `main.go` de tabs a espacios en un multi-edit; detectado por
`gofmt -l` en el smoke de cierre y restaurado con `gofmt -w`
(dif verificado: solo whitespace). Lección operacional nueva para los
informes: en este entorno, las old/new-strings de edición deben
extraerse de los BYTES del fichero (grep/python), nunca de la
renderización del Read.
