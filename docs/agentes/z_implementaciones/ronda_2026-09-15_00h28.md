## Mejora 1 — Comando `doctor` (diagnóstico de lab)

- **Motivación:** hasta ahora, diagnosticar por qué un lab no funcionaba
  requería encadenar `status`, `stats`, `list`, `keylog` y mirar permisos a
  mano. `doctor` lo resume en un comando con veredicto claro — y detecta el
  desajuste de versión cliente/módulo, que hasta ahora solo se manifestaba
  como `ENOTTY` críptico.
- **Checks que ejecuta:**
  1. nodo `/dev/vault_kernel` presente (con modo exacto del nodo);
  2. apertura RW (diagnostica `EACCES`/`EPERM` con acción sugerida);
  3. `GET_STATS` responde (parseo `clave=valor`) y muestra versión/uptime;
  4. comparación de versión cliente vs módulo (WARN si difieren);
  5. hooks instalados vs planificados (WARN si 0 — features inactivas);
  6. estado stealth vía `/sys/module/vault_kernel` (INFO, nunca warn);
  7. interfaz keylog legible;
  8. interfaz list legible.
  Salida no-cero solo si el módulo es inalcanzable; los warnings no fallan.
- **Archivos:** `client/go/cmd/vault_kernel/main.go` (`runDoctor()`, constantes `sysfsModulePath`), `client/vault_kernel_cli.py` (`run_doctor()`, constantes `SYSFS_MODULE`, subparser `doctor`).
- **Cómo probarla:** con el módulo cargado en la VM de lab:
  `sudo ./vault_kernel doctor` (Go) o `sudo python3 client/vault_kernel_cli.py doctor`.
  Sin módulo: `[FAIL] /dev/vault_kernel not found — module is not loaded` y exit 1 (verificado aquí).

## Mejora 2 — `give-root` con verificación post-ioctl

- **Motivación:** el CLI reportaba "[+] Granted root" solo por el exit code
  del ioctl, sin verificar el efecto. Como el ioctl corre en el task del
  propio CLI, el camino self es verificable al instante con `geteuid()`;
  el camino remoto, leyendo `Uid:` de `/proc/<pid>/status`.
- **Comportamiento nuevo:**
  - self: `[+] Granted root to PID N (verified: euid=0)` — o `[?]` si el ioctl
    devolvió 0 pero el euid no cambió (señal de que algo va mal en el módulo);
  - remoto: verifica vía `/proc/<pid>/status` (tercer campo de `Uid:` = euid)
    y reporta el resultado de la verificación.
- **Archivos:** `client/go/cmd/vault_kernel/main.go` (`verifyRootSelf()`, `verifyRootRemote()`, `giveRoot()`), `client/vault_kernel_cli.py` (`_proc_euid()`, `give_root()`).
- **Cómo probarla:** en la VM: `sudo ./vault_kernel give-root` debe mostrar
  `(verified: euid=0)`; `sudo ./vault_kernel give-root <pid-de-otro-proceso>`
  debe añadir la línea `Verified via /proc/<pid>/status: euid=0`.

## Mejora 3 — Validación de entrada contra los buffers fijos del kernel

- **Motivación:** `hide-file` con nombres > 255 bytes se truncaba en
  silencio (`copy(buf, name)` en Go, `ljust(256)` en Python): el módulo
  ocultaba un nombre distinto al tecleado y el operador creía que funcionaba.
  Lo mismo para la palabra mágica (> 15 chars, se pisaba el NUL) y el target
  de shell (> 255 bytes). Ahora se rechazan con error claro y exit 1.
- **Archivos:** ambos CLIs (`hideFile`/`unhideFile`/`backdoorShell`/`backdoorMagic` en Go; `_reject()` + los mismos métodos en Python).
- **Cómo probarla:** `./vault_kernel hide-file aaa…(300)` →
  `[-] Error: name too long (300 bytes): the kernel hide-list stores at most 255`
  (verificado en este entorno, exit 1; el mensaje Python es equivalente).
