## Entrega 1 — `capture --out FILE --stdout` (Go + Python)

- **Motivación:** el backlog de v3.9 lo dejó escrito — "para BOTH
  (fichero y stdout) hace falta un flag explícito, no el marker `-`"
  (que la regla de valores con `-` de v3.10 habría rechazado). Un
  operador de lab quiere ARCHIVAR la evidencia y VERLA (o piparla) en
  el mismo comando.
- **Diseño:** `--stdout` es booleano, como mucho una vez; con
  `--out FILE` escribe el fichero 0600, imprime el documento JSON en
  stdout y manda el resumen de una línea a STDERR — `capture --out
  ev.json --stdout | jq` queda como pipeline limpio. Sin `--out` se
  acepta y es un no-op documentado (scripts pueden pasarlo
  incondicionalmente). Gramática extendida en `parseCaptureArgs`
  (ahora devuelve `(outPath, forceStdout, error)`; `--stdout`
  duplicado = error de uso) y espejo exacto en argparse
  (`store_true`).
- **La matriz de entrega vive en una función pura** (patron build/
  render de rondas previas): Go extrae `emitCaptureBundle(j, outPath,
  forceStdout)` — testeable con directorio temporal y captura de
  streams por pipes (`captureStdoutStderr`); Python lo resuelve dentro
  de `capture(out, to_stdout)` con `print(..., file=sys.stderr)`.
- **Tests:** Go — `TestParseCaptureArgs` extendido (6 casos nuevos:
  --stdout solo, en ambas posiciones, duplicado, etc.) y
  `TestEmitCaptureBundle` (4 escenarios: stdout puro, fichero+resumen
  en stdout, fichero+JSON en stdout+resumen en stderr con permiso
  0600 verificado, ruta no escribible → error envuelto). Python —
  `TestCaptureStdoutFlag` (3 tests: fichero+stdout con JSON parseado,
  stderr con el resumen y fichero 0600; `--stdout` sin `--out`; y
  gramática argparse).
- **Wiring:** usage Go y epílogo del CLI Python; completions bash y
  zsh (`capture → --out --stdout`); contrato actualizado en
  `docs/schemas/capture.md` (ROL 3).
- **Cómo probarla:** en VM: `sudo ./vault_kernel capture --out ev.json
  --stdout | jq .schema` → `1` con el resumen visible en stderr; sin
  módulo, la gramática se verifica por `go test -run
  TestEmitCaptureBundle -v`.

## Entrega 2 — `keylog --follow --stop-after N` (Go + Python)

- **Motivación:** backlog #5 — ventanas de captura finitas para
  scripts: "graba 200 eventos y sal limpio" sin `timeout` externo ni
  `pkill`, con el fichero de salida cerrado ordenado.
- **Diseño:** `--stop-after N` requiere `--follow` (mismo criterio que
  `--timestamps`: el one-shot lee exactamente un buffer), N >= 1
  entero, como mucho una vez. En el bucle, tras emitir el evento N se
  imprime la despedida estándar `\n[*] Follow stopped` y se retorna
  nil — UN SOLO camino de parada limpio para Ctrl-C, SIGTERM y
  stop-after (el sink se cierra por defer/finally en los tres). El
  banner del stream anuncia el límite: `[*] Following keystroke log
  (poll 500 ms, stop after 200 events) — Ctrl-C to stop`.
- **Go:** `keylogOpts.stopAfter` (0 = ilimitado);
  `parseKeylogArgs` valida operand (missing/duplicado/`< 1`/no
  numérico = error de uso con el token en el mensaje); `keylogFollow`
  lleva el contador `emitted`. Python: tipo argparse
  `_stop_after_arg` (int >= 1, errores `ArgumentTypeError` espejo) y
  guard `stop_after is not None and not follow → SystemExit` ANTES de
  `self._open()` (paridad con Go post-apertura documentada de ronda 4:
  Go valida la gramática tras abrir; Python, antes — el test de
  Python cubre el guard, el de Go el parser).
- **Tests:** Go — `TestParseKeylogArgsStopAfter` (3 válidas en ambos
  órdenes, sin-follow, missing operand, 0, -3, abc, duplicado,
  default 0). Python — `TestKeylogStopAfter` (3 tests: tipo argparse
  con 0/-3/abc rechazados, guard requires-follow, y **test de bucle
  real** con ioctl simulado que entrega 4 deltas: el stream emite
  "aaa"+"bbb", para tras N=2 con la despedida, y el sink contiene
  exactamente los eventos emitidos — sin "ccc").
- **Wiring:** usage Go (línea `keylog` + explicación), epílogo Python,
  completions bash+zsh (`keylog → ... --stop-after`).
- **Cómo probarla:** en VM: `sudo ./vault_kernel keylog --follow
  --stop-after 5 --output cap.log` — tras el quinto evento el CLI
  termina solo con `[*] Follow stopped` y `cap.log` queda cerrado con
  5 registros.

## Entrega 3 — Autocompletado zsh + paridad blindada (bash ya existente)

- **Motivación:** backlog #4 (arrastrado desde v3.9). El proyecto
  mantiene DOS clientes por contrato de paridad; los completados no
  podían ser la excepción — y la deriva bash↔zsh era el riesgo
  evidente de mantener dos ficheros a mano.
- **Diseño:** `completions/vault_kernel.zsh` (`#compdef vault_kernel
  vault_kernel_cli.py`) — solo builtin (`compdef`/`_arguments`/
  `_describe`/`_files`, sin paquetes), misma superficie: 22 comandos
  con descripciones, flags por comando espejo del bash (incluidos los
  NUEVOS `--stdout` y `--stop-after`), `_files` para hide-file/
  unhide-file y para `--output`/`--out`.
- **Paridad blindada por test** (la decisión de diseño clave):
  `tests/test_completions.sh` gana una sección que compara
  TEXTUALMENTE ambos ficheros — los 22 comandos y los 9 flags deben
  aparecer en los DOS — más `zsh -n` cuando zsh está instalado (skip
  documentado y determinista cuando no: la paridad textual corre
  SIEMPRE). El test demostró su valor en esta misma ronda: falló al
  primer intento porque el bash aún no tenía los flags nuevos —
  se corrigió el bash y pasó.
- **Tests:** 15/15 checks al cierre (12 previos + file-exists +
  paridad comandos + paridad flags).
- **Cómo probarla:** `mkdir -p ~/.zsh/functions && cp
  completions/vault_kernel.zsh ~/.zsh/functions/_vault_kernel &&
  fpath=(~/.zsh/functions $fpath) && autoload -Uz compinit &&
  compinit` → `vault_kernel keylog --<TAB>` ofrece los 5 flags.
