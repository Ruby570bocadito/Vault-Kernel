## Corrección 1 (ALTA) — CI en rojo: `write()` sin comprobar en el stager C

- **Descripción:** el job "Payload regression" falla desde v3.3 (también
  rojo en `ba2171d`; los 6 jobs restantes pasan). El stager C generado
  ejecutaba `write(fd, data, len);` descartando el resultado; la glibc de
  Ubuntu (FORTIFY activado por defecto) declara `write` con `__wur` →
  warning `-Wunused-result` → el check "gcc emitted warnings" del test
  falla. En local no se ve porque este entorno no habilita FORTIFY.
- **Severidad:** ALTA (CI global en rojo: el pipeline deja de ser señal
  fiable de regresión).
- **Causa raíz:** diferencia de entorno (FORTIFY) + valor de retorno
  ignorado; un `write` corto además habría producido un `.ko` corrupto.
- **Solución:** `if (write(fd, data, len) != (ssize_t)len) { perror("write"); close(fd); free(data); return 1; }` en la plantilla del stager.
- **Archivos:** `payloads/payload.py` (plantilla C del stager).
- **Cómo verificarlo:** (1) `bash tests/test_payloads.sh` → 13/13; (2)
  compilar el stager generado con `-O2 -Wall -D_FORTIFY_SOURCE=2` (réplica
  del runner): **cero warnings** — sin el fix, el warning es reproducible
  con ese mismo comando; (3) el job de CI debe pasar en este push.

## Corrección 2 (MEDIA) — EOF prematuro cuando una tanda completa está oculta

- **Descripción:** si TODAS las entradas de una tanda de `getdents` estaban
  ocultas, el hook devolvía 0 → el proceso interpretaba EOF y **dejaba de
  ver los ficheros visibles de tandas posteriores** del mismo directorio.
- **Severidad:** MEDIA (pérdida silenciosa de visibilidad — tanto para el
  operador del lab como para la fiabilidad del experimento).
- **Causa raíz:** el hook trataba "tanda filtrada a cero" como fin de
  directorio; el original ya había avanzado `file->f_pos`, así que bastaba
  pedir la siguiente tanda.
- **Solución:** `hooked_getdents64`/`hooked_getdents` iteran en bucle: se
  devuelve 0 solo cuando el `getdents` original devuelve EOF real; cuando
  una tanda aporta entradas visibles se devuelve el reporte filtrado
  (`kept`). Cada iteración libera su buffer (`kmalloc`/`kfree` emparejados).
- **Archivos:** `src/file_hide.c` (ambos hooks + comentarios de diseño).
- **Cómo verificarlo:** (1) arnés `scripts/proof_getdents_flow.c` (fuera
  del repo): directorio en 3 tandas `[A,OCULTO] [OCULTO,OCULTO] [B,C] EOF`
  — bucle v3.3 entrega 1/3 visibles (pierde B y C), bucle v3.5 entrega
  3/3 y respeta EOF; con el directorio totalmente oculto devuelve EOF en
  la primera llamada (comportamiento intencionado, sin bucle infinito);
  (2) en la VM: ocultar el único fichero de un directorio en `/tmp` y
  listar el padre — los demás directorios siguen apareciendo.

## Corrección 3 (BAJA) — CLIs de 32 bits recibían `ENOTTY`

- **Descripción:** `vault_kernel_fops` solo registraba `.unlocked_ioctl`;
  un proceso de 32 bits sobre kernel de 64 (vía compat) obtenía `ENOTTY`
  para todos los comandos.
- **Severidad:** BAJA (los CLIs suministrados son de 64 bits; afecta a
  tooling externo compilado en 32 bits).
- **Causa raíz:** handler compat no registrado.
- **Solución:** `.compat_ioctl = vault_kernel_ioctl` — todos los comandos
  pasan `_IO` (sin argumento) o buffers de tamaño fijo (256/16/4/2/4096),
  así que el puntero compat zero-extended llega al mismo handler sin
  traducción por comando. Nota: `compat_ptr_ioctl` (helper del kernel)
  no se usa para no condicionar a kernels ≥ 5.5.
- **Archivos:** `src/ioctl.c` (fops).
- **Cómo verificarlo:** en la VM, compilar el CLI Go con `GOARCH=386`
  (o el CLI Python de un intérprete 32-bit) y ejecutar `stats` — debe
  responder igual que el de 64 bits.

## Recomendaciones de seguridad generales para el resto de agentes

1. **Cada valor de retorno de syscall/libc en plantillas de payload debe
   usarse o explicitarse** — con FORTIFY, ignorar `write`/`fread`/etc.
   rompe la CI en runners Ubuntu aunque local compile limpio. Probar las
   plantillas con `-D_FORTIFY_SOURCE=2` antes de pushear.
2. **Cuidado con los bucles de reintento en hooks:** siempre con avance
   garantizado (`f_pos` avanza por el original) y buffers liberados por
   iteración — revisar el emparejamiento kmalloc/kfree de cada rama.
3. Las plantillas de payload son código C que vive en un string de
   Python: cualquier cambio debe re-verificarse compilándolo (ya lo hace
   `tests/test_payloads.sh`; añadir FORTIFY al job es opción futura).
