## Corrección 1 (BAJA agregada, sistémica) — gramática Go permisiva en 15 de 20 cases

- **Descripción:** el dispatcher Go validaba el MÍNIMO de operandos
  pero nunca rechazaba el EXCESO: `hide-file a b` ocultaba "a" e
  ignoraba "b"; `watch --interval 500 extra` ignoraba "extra";
  `list extra` listaba igual; `list --json extra` ignoraba el extra;
  `keylog-clear extra`, `status extra`, `version extra`,
  `doctor extra`, `magic w extra`, `magic-encode w p extra`,
  `hide-pid 1 2`, `hide-port 80 443`, `reset extra`... todos
  tolerados en silencio. El CLI Python (argparse) rechaza TODOS esos
  inputs. Mismo comando, dos gramáticas según cliente — y en Go los
  argumentos ignorados podían contener el operand que el operador
  CREÍA aplicado (`hide-file a b` oculta solo "a": error de
  semántica silencioso en el plano de control).
- **Causa raíz (estructural, no puntual):** el dispatcher creció por
  adición de cases, cada uno con su validación ad-hoc de "mínimo de
  operandos"; no existía una regla global de gramática. Las rondas 4-5
  extractaron parsers puros para `give-root` y `keylog`, pero la clase
  siguió viva en los otros 15 cases.
- **Solución (regla global + parsers puros):**
  - `strictArgs(args, want, usage)` — exactamente `want` operandos;
    el error nombra el PRIMER argumento inesperado
    (`unexpected argument: b`). Aplicado a hide-file/unhide-file,
    shell, magic, hide-pid/unhide-pid (vía wrapper), hide-port/
    unhide-port (vía wrapper) y los comandos de cero operandos
    (status, version, keylog-clear, hide-module, unhide-module, reset).
  - `parseFlagOnly(args, flag, usage)` — gramática estricta de los
    comandos cuyo único argumento es un flag opcional (doctor/list/
    stats `--json`): nada, el flag una vez, o error de uso.
  - `parseWatchArgs(args)` (pura) — `watch [--interval MS]`: default
    1000, operand obligatorio (≥ 50 ms, mismo suelo que keylog),
    cualquier token extra o desconocido es error de uso.
  - `parseMagicEncodeArgs(args)` (pura) — exactamente `<word> <port>`,
    port 1-65535 vía el nuevo `parsePortArg` (que además deduplica la
    validación de puerto que estaba copiada tres veces inline).
  - `help`/`-h` queda deliberadamente permisivo (decisión del
    Director, documentada: es una página de ayuda, no una operación
    con estado).
- **Archivos:** `client/go/cmd/vault_kernel/main.go` (7 funciones
  nuevas + dispatcher reescrito case a case),
  `main_test.go` (`TestStrictArgs`, `TestParseFlagOnly`,
  `TestParseWatchArgs`, `TestParseMagicEncodeArgs`,
  `TestParsePortArg`).
- **Cómo verificarlo:** `go test ./cmd/vault_kernel/ -run
  'TestStrictArgs|TestParseFlagOnly|TestParseWatchArgs|TestParseMagicEncodeArgs'
  -v`; smoke real sin módulo: `./vault_kernel magic-encode pwn 4444
  extra` → `usage: vault_kernel magic-encode <word> <port>`;
  `./vault_kernel version extra` → `usage: vault_kernel version
  (unexpected argument: extra)` (verificado en este entorno con el
  binario construido).

## Corrección 2 (BAJA, validación de entrada sensible) — `shell` sin validación real de `ip:port`

- **Descripción:** Go solo exigía `strings.Contains(target, ":")` —
  `shell abc:def` pasaba el cliente y moría en el kernel con un EINVAL
  crudo (`src/ioctl.c` parte en el PRIMER `:`; `backdoor_trigger_shell`
  hace `kstrtoint("def")` → falla). El CLI Python NO validaba NADA:
  cualquier string llegaba al ioctl. En ambos, el módulo era la única
  barrera — y un EINVAL crudo no le dice al operador QUÉ está mal.
- **Severidad:** BAJA (lab tool; el módulo nunca llega a spawnear con
  puerto inválido), pero es el plano de control de un backdoor: el
  input debe validarse ANTES del ioctl, con errores accionables.
- **Solución:** `parseShellTarget(target)` (Go, pura) y
  `_shell_target_arg` (Python, argparse type): EXACTAMENTE un `:` (el
  módulo parte por el primero — con 2+ colons, IPv6 literales
  incluidos, el target llegaría mutilado: se rechaza en el cliente
  con mensaje claro "IPv6 not supported" en vez de EINVAL del kernel),
  host no vacío, puerto numérico 1-65535. Composición estricta con el
  resto de la gramática (extras rechazados por `strictArgs`).
- **Archivos:** `main.go` (`parseShellTarget` + case `shell`),
  `main_test.go` (`TestParseShellTarget`: 4 válidos, 9 inválidos),
  `vault_kernel_cli.py` (`_shell_target_arg` + subparser),
  `test_cli_parsing.py` (`TestShellTargetArg`).
- **Cómo verificarlo:** `go test ./cmd/vault_kernel/ -run
  TestParseShellTarget -v`; Python: `python3 client/vault_kernel_cli.py
  shell abc` → `invalid target 'abc': use ip:port (IPv6 not
  supported)`; `shell 1.2.3.4:4444` pasa la validación y llega al
  aviso de dispositivo (verificado en este entorno).

## Corrección 3 (BAJA, integridad de datos del plano de control) — `hide-pid`/`unhide-pid` aceptaban pid ≤ 0

- **Descripción:** ambos clientes aceptaban 0/negativos. El módulo
  (`proc_hide_add`) almacena CUALQUIER int verbatim: `hide-pid -5`
  produce una entrada `pid: -5` en `list` que NADA puede igualar
  nunca (`hooked_kill` filtra solo pid > 0; `is_proc_pid_hidden`
  parsea dígitos de nombres /proc). Datos sin sentido en el estado
  del implante + un `unhide-pid -5` que "funciona" sin hacer nada.
- **Contrato kernel NO cambia:** pid ≤ 0 solo tiene semántica "caller"
  en GIVE_ROOT (documentada); para HIDE_PID no hay contrato — es
  entrada basura que el cliente debe filtrar.
- **Solución:** `parsePIDArg` (Go, pura: numérico ≥ 1) + wrapper
  `parsePIDArgs` (gramática de un operand); Python `_pid_arg` (argparse
  type). give-root NO se toca: su contrato pid ≤ 0 = self es distinto
  y está documentado.
- **Archivos:** `main.go`, `main_test.go` (`TestParsePIDArg` +
  wrapper), `vault_kernel_cli.py`, `test_cli_parsing.py`
  (`TestPidArg`).
- **Cómo verificarlo:** `go test -run TestParsePIDArg -v`;
  `python3 client/vault_kernel_cli.py hide-pid -5` → `PID must be >= 1,
  got -5` (verificado en este entorno); en VM, `hide-pid 0` debe dar
  error de uso en ambos clientes.

## Corrección 4 (BAJA, paridad/UX) — `keylog` one-shot de Python con buffer vacío no imprimía nada

- **Descripción:** el flujo v3.8 de `keylog_read` imprimía DENTRO de
  `if cur != prev:` — con buffer vacío, `cur == prev == ""` y el print
  caía en la rama que no se ejecuta: el comando terminaba en silencio
  total. El CLI Go imprime `[*] (no keystrokes captured)`. Mismo
  comando, dos comportamientos; el silencio parece un fallo del CLI.
- **Causa raíz:** el diff de follow y la impresión one-shot vivían en
  el mismo bloque condicional; el camino one-shot nunca tuvo test del
  caso vacío.
- **Solución:** el camino one-shot se reestructura (dentro de la
  implementación de `--output` de ROL 2; el análisis y la regresión
  son de este rol): imprime SIEMPRE (buffer o mensaje informativo) y
  sale; el diff/sink vive solo en follow. Test de regresión:
  `test_oneshot_empty_writes_nothing` (mensaje presente, fichero NO
  creado).
- **Cómo verificarlo:** `python3 tests/python/test_cli_parsing.py
  TestKeylogOutput -v`; en VM: `keylog-clear && vault_kernel_cli.py
  keylog` → mensaje informativo (antes: nada).

## Recomendaciones de seguridad generales para el resto de agentes

1. **La regla global existe ahora:** TODO comando nuevo nace con su
   parser puro (o `strictArgs`/`parseFlagOnly` si es trivial) y con el
   rechazo de exceso desde el día uno. El patrón "mínimo de operandos
   y el resto se ignora" está erradicado del dispatcher.
2. **La validación de entrada sensible vive en el cliente, con errores
   accionables:** el módulo es la última barrera, no la primera
   (`shell`/`hide-pid` lo demuestran). Un EINVAL crudo del kernel no
   es una UX de seguridad aceptable cuando la validación es barata en
   userland y testeable sin VM.
3. **Paridad de gramática incluye los caminos de error Y los casos
   vacíos:** el caso "buffer vacío" de keylog one-shot llevó tres
   rondas sin test. Regla: cada camino de salida de un comando (ok,
   vacío, error de uso, error de dispositivo) tiene al menos un test
   en un cliente y espejo en el otro cuando es observable.
4. **`od -c`/`grep -F` como única fuente de verdad para caracteres, y
   scripts que preserven bytes para ficheros sensibles a indentación:**
   esta ronda sumó el incidente Makefile (TABs→espacios por el editor;
   detectado por `make -n`, restaurado). El Makefile se edita SOLO con
   scripts a partir de ahora; `make -n` es su smoke test obligatorio.
5. **Nota operacional recurrente:** el token de GitHub del owner sigue
   expuesto en el chat desde la ronda 1. El repo está limpio (verificado
   con `git grep` + `git log -S`), pero el token debe rotarse/revocarse
